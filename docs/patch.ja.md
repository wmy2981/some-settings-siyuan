# ユーザーレベルの宣言パッチ：`.patch.yml`

機能をそもそも提供するか、どの設定タブに属するか、どのフロントエンドに適用するか、どの SiYuan バージョンに
対応するかは、いずれもプラグインのソースにある機能宣言で決まり、プラグインと一緒にリリースされます。
インターフェースのテキストも、プラグインに同梱される言語ファイルから読み込まれます。こうした内容の一部を
自分のマシンで変更したい場合（たとえばある機能を完全にオフにする、別のタブへ移す、モバイルのフロントエンド
だけに表示する、いくつかのインターフェーステキストを書き換えるなど）は、プラグインのストレージディレクトリに
`.patch.yml` を置いて管理できます。プラグインは機能を読み込む**前に**これを適用します。

このファイルは**あなた自身が管理するもの**です。プラグインはテンプレートを作成せず、設定パネルに入口も
用意せず、変更も監視しません。設定パネルにこのファイル用の行、ボタン、説明が増えることはありません。

## ファイルの場所

```
<workspace>/data/storage/petal/some-settings-siyuan/.patch.yml
```

ファイル名は固定で、先頭がドットです。各機能自身の `feature-<id>` 設定ファイルと同じディレクトリに置きます。
ファイルが存在しない場合は単に「パッチなし」を意味し、これが通常の状態です。プラグインはこのファイルを
作成せず、何も通知しません。

## フィールド

機能宣言はトップレベルのキー `features` の下に、**機能 id** ごとにまとめて書きます。各機能では、次の 5 つの
フィールドのいずれか、またはすべてを指定できます。フィールドを省略した場合はソースの宣言がそのまま使われ、
制限が**解除されるわけではありません**。

| フィールド      | 上書きする内容                                     | 有効な値                                                                                                                  |
| --------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `enabled`       | 機能をプラグインと一緒に提供するか                 | `true` / `false`                                                                                                          |
| `category`      | 機能が属する設定タブ（複数可）                     | `ai` / `editor` / `doc-tree` / `appearance` / `connection` / `settings` / `bazaar` / `plugin`、またはこれらのリスト       |
| `frontends`     | 適用するフロントエンド                             | `desktop` / `mobile` のリスト。`[]` はどちらのフロントエンドでもないことを意味し、`null` または空の値は制限なしを意味する |
| `minAppVersion` | 対応する最も低い SiYuan バージョン（この値を含む） | `"3.8.7"` のような SiYuan のバージョン文字列。`null` または空の値は下限を解除する                                         |
| `maxAppVersion` | 対応する最も高い SiYuan バージョン（この値を含む） | `"3.9.0"` のような SiYuan のバージョン文字列。`null` または空の値は上限を解除する                                         |

`category` に書くのはタブのラベルではなくタブ id です。`[editor, doc-tree]` のようなリストを書くと、機能を
複数のタブに同時に表示できます。リストを空にしたり、同じタブを重複させたりはできません。バージョン番号は
引用符で囲んでください。`3.8` は有効なバージョンではなく、`"3.8.7"` が有効です。

## 例

```yaml
features:
  # 「Enter でエージェントのメッセージを送信」をオフにする。設定は読み込まれず、
  # マウントもされず、既定では設定パネルにも表示されない
  agent-enter-to-send:
    enabled: false

  # 「エディタ」タブに移し、両方のフロントエンドに適用する
  desktop-command-panel-slim:
    category: editor
    frontends: [desktop, mobile]

  # 「エディタ」と「ドキュメントツリー」の両方のタブに表示する
  heading-level-icon:
    category: [editor, doc-tree]

  # 自分の SiYuan バージョンでのみ試す
  tab-title-markdown:
    minAppVersion: "3.8.7"
    maxAppVersion: "3.9.0"

  # ソースの 2 つの制限を解除する。フロントエンドの制限も含む
  mobile-console-log:
    frontends: null
    maxAppVersion: null
```

1 つの機能に複数のフィールドを書くこともでき、効果は重なります。`frontends` はブロックリストとして書くことも
できます。

```yaml
features:
  mobile-dock-blur:
    frontends:
      - mobile
```

## 制限の解除

ソースがすでに `maxAppVersion` を宣言している場合（上流がその機能を実装したら、このパッチは役目を終えます）、
そのフィールドを**省略しても何も変わりません**。機能は新しい SiYuan バージョンでも従来どおり非表示になります。
そこでも表示させたい場合は、空の値を明示的に書く必要があります。

```yaml
features:
  tab-title-markdown:
    maxAppVersion: null # `maxAppVersion:` と書いても同じ意味
```

`minAppVersion` と `frontends` も同じです。逆に、`frontends: []` は「両方のフロントエンド」ではなく
「どちらのフロントエンドでもない」を意味します。`enabled` に触れずに自分のマシンで機能を止めたいときは、
空のリストを使ってください。

## インターフェースのテキストを上書きする（i18n）

パッチは機能宣言に加えて、プラグインに同梱されるテキストもインターフェース言語ごとに上書きできます。
トップレベルのキーが `i18n`、2 番目の階層が言語コード、3 番目の階層が i18n キーとそのテキストです。

```yaml
i18n:
  en:
    feature.clearConfig.action: "Clear everything"
    panel.unavailable.frontend: "Only available on {platform}"
```

* **適用されるのは現在のインターフェース言語だけです。** プラグインは実行時に 1 つの言語ファイル（その
  インターフェース言語のもの）だけを読み込むため、ほかの言語のセクションは適用されず、その値も検証されません。
  ただし、`i18n` 全体の形（言語 → キーと値の表）は有効である必要があります。言語コードは `zh-CN` でも、
  従来のアンダースコア表記 `zh_CN` でも書けます。
* **変更できるのは既存のキーだけです。** キーはプラグインに同梱される言語ファイルにすでに存在している必要が
  あり、存在しないキーはスキップされます（次の小節を参照）。値はそのまま使われます。`{platform}`、
  `{version}`、`{count}` などのプレースホルダーは、そのテキストを使うコードが従来どおり置き換えます。
  これは、その文を `i18n/<language>.json` に直接書いた場合とまったく同じです。

### 存在しない機能 id と i18n キー

パッチで指定した機能 id や i18n キーがこのマシンに存在しない場合（打ち間違い、またはプラグインの
アップグレードでその機能やテキストが削除された場合）、その 1 件だけが**通知なしにスキップ**され、残りは
そのまま適用されます。そのため、古いパッチはテキストが削除されるアップグレードを越えて生き残ります。
代わりに、打ち間違いは一切エラーにならず、詳細ログの `skipped unknown …` の行だけが手がかりになります。

## 反映されるタイミング

* ファイルは**プラグインの読み込み時**に 1 回だけ読み込まれます。編集した後は「設定 → マーケットプレイス →
  ダウンロード済み → Some Settings」でプラグインを無効にしてから有効にするか、プラグインを再読み込みして
  ください。ファイルを監視するものはありません。
* テキストの上書きは、どの機能がマウントされるよりも前に、ホストがすでに読み込んだ言語ファイルへ書き込まれ
  ます。そのためパネル、メッセージ、アクションボタン、各機能の表示はすべてパッチ後のテキストになり、パネルの
  検索もそのテキストに一致します。
* パッチが変えるのは**機能の提供に関する宣言**であり、各機能のパネルにある実行スイッチではありません。
  `enabled: false` でオフにした機能は読み込みすらされません。パッチで再び有効にした機能も、実際に動作するには
  その機能自身のスイッチをオンにする必要があります。
* 機能をオフにすることは、プラグインがその機能を提供しないことを意味します。設定は読み込まれず、マウントも
  されず、既定では設定パネルにも表示されません。「このプラグイン」タブで「利用できない設定を表示」をオンに
  すると、その機能は自分のタブの最下部にグレー表示され、理由には「パッチによって無効化されています」と
  表示されます。
* パッチはカテゴリも変更できます。通常の項目もグレー表示の項目も新しいタブ（複数のタブも可）へ移動し、
  タブ内の順序は登録順のままです。
* パッチはフロントエンドとバージョン範囲も変更できます。表示されない理由はパッチ後の宣言から再計算される
  ため、ソースの宣言に対応する理由が残ることはありません。

## エラーが起きたとき

**どこか 1 か所でも不正があれば、ファイル全体が無効になります**。すべての機能はプラグインに同梱される宣言に
戻り、一部だけが適用された状態になることはありません。（唯一の例外は、存在しない機能 id や i18n キーです。
その 1 件はスキップされます。前述のとおりです。）無効になる理由には次のものがあります。

* YAML の構文エラー（メッセージに行番号が付きます）。
* `features` と `i18n` 以外のトップレベルのキーがある、または `features` が「機能 id → フィールド」の対応に
  なっていない。
* 不明なフィールド、または型が正しくない値。
* `i18n` が「言語 → キー → テキスト」の構造になっていない、または現在の言語に存在するキーの値が文字列で
  ない（空の文字列も同様に無効です）。存在しないキーはその値ごとスキップされます。
* 不正な `category`、不正なフロントエンド、重複したフロントエンド。
* 不正なバージョン番号、またはソースの宣言とマージした結果 `minAppVersion` が `maxAppVersion` を上回って
  空になるバージョン範囲。

その場合：

* プラグインは通常どおり起動し、設定の入口、設定パネル、その他の機能はすべて動作し続けます。壊れたパッチが
  何かを妨げることはありません。
* 詳細ログをオンにしている場合、コンソールに理由を添えた `WARN` が 1 行出力されます（ファイルの内容は
  出力されません）。
* このプラグインの設定パネルを開くたびに、パッチが無効であることを知らせる非ブロッキングのメッセージが
  表示されます。パッチにはパネル内の項目がないため、このメッセージがなければコンソールを読むまで気づけません。
* ファイルがない、空のファイル、コメントだけのファイル、`features: {}`、`i18n: {}` はいずれも「上書きなし」を
  意味し、エラーにはなりません。

## メンテナンスの範囲

* 「設定をエクスポート」「設定をインポート」「このプラグインの設定を消去」は、ディレクトリ内の `feature-*`
  設定ファイルだけを扱います。`.patch.yml` は**対象外**で、これらの操作が変更することはありません。
* プラグインをアンインストールしても、プラグインのストレージディレクトリから何も削除されません。`.patch.yml` と
  各機能の設定はそのまま残り、再インストール後も同じように適用されます。
* パネルとその検索にパッチ自体が現れることはありません。項目も、コントロールも、パスも、内容も、状態も
  表示されません。`i18n` のセクションは既存のテキストを上書きするだけで、どこからも参照されないキーを
  追加することはできません。

## 対応する YAML の書き方

このファイルに実際に必要な構文だけを受け付け、それ以外は推測せずエラーにします。

* ブロックマッピング。インデントには空白だけを使います（1 階層に 2 つの空白が無難です）。
* 値：空の値（`key:`、`null`、`~`）、`true` / `false`、プレーンテキスト、シングルクォートとダブルクォートの
  文字列、インラインリスト `[a, b]`、空のマッピング `{}`、ブロックリスト（1 行に 1 項目 `- a`）。
* コメント：行全体の `# …`、または値の後ろに空白を挟んだ `# …`（引用符の中の `#` はコメントでは
  ありません）。

対応していないもの：アンカーとエイリアス（`&` / `*`）、複数ドキュメント（`---`）、ブロックスカラー（`|` / `>`）、
`{}` 以外のインラインマッピング、タグ（`!!`）、タブによるインデント、あいまいな真偽値 `yes` / `no` / `on` / `off`。
真偽値は `true` / `false` と書いてください。

> パッチは上級者向けの入口です。無理にオンにした機能や、フロントエンドとバージョン制限を変更した機能が
> 正しく動作することは、プラグインは保証しません。
